# 任务日期错误修复（2026-11-17）

## 问题与证据

用户请求：“创建一个任务，今天下午16:00-17:00，主题是完成重复规则需求不明确的规则的梳理和编写”。

只读核对本地状态与工具 Trace：原消息时间为北京时间 2026-11-17 15:16:01.581。模型调用创建任务工具时，已经传入 `dueTimestamp=1793005200000`（2026-10-26 17:00），并在说明中写了 10 月 26 日的时间段。授权待办保存了同样的错误日期；飞书返回的截止时间与提交值一致，开始时间为空。

根因：任务链路没有日程链路已有的相对日期校正，直接信任模型计算的时间戳；任务 schema 和 API 映射只有截止时间，没有开始时间。OAuth 忠实续办了已经错误的输入。

## 修复

- 新增任务开始时间字段，创建和更新均映射到飞书 Task v2 `start`；`start` 和 `due` 使用毫秒时间戳及 `is_all_day=false`。
- 在资源操作入口，依据原消息及其可信时间校正单一明确日期。明确的 `16:00-17:00` 时段同时生成开始、截止字段，并校正生成的纯时间窗口说明；保留其他说明内容。
- 在授权前保存校正结果；恢复旧待办时也依据已保存的原消息校正，再发送操作审批。跨午夜授权不使用回调当天重新解释“今天”。
- 已确认的写入执行阶段不重新解释日期；已完成的线上任务没有自动改动。
- 审批及结果摘要显示开始和截止的北京时间。部分时间编辑在审批前回读未修改的端点，拒绝倒置时间段。
- Agent/工具说明明确要求用结构化字段传递时段。

## 验证与范围

回归覆盖原始案例、已有授权、未授权到写入审批及最终 API 请求、跨午夜授权、升级前保存的授权待办、仅修改开始时间、部分修改与现有端点冲突、北京时间日界线、完整年月日、次日/后天、无效时间、标题中的日期和说明保留。

修复前新增的开始时间更新用例失败（schema 丢弃字段，API 报 No task fields to update）。修复后 `npm test` 全部 21 个测试文件、222 项测试通过；`npm run typecheck`、`git diff --check` 和 `npm run build` 均通过。最终构建于北京时间 2026-11-17 15:27:23 成功，含生成目录依赖安装。

日期校正只处理单一明确的今天/明天/后天或完整年月日，不以简化解析器重写多日期、多时段和其他复杂自然语言。复杂时间仍由 Agent 理解并经操作卡确认。

按当前会话规则执行内联代码审查，未派发子代理。检查重点：OAuth 不重算相对日期、已确认操作不静默修改、毫秒单位一致、仅修改一个端点时的校验、用户说明不被覆盖。
